# 智拓 · 政企企业评分模型（v1）说明

> **一句话**：输入一份企查查导出的企业清单，输出每家企业 0–100 的拜访优先级评分 +
> S/A/B/C/D 分级 + 移动政企方案线标签 + 联系方式，让客户经理知道「先拜访谁、带什么方案」。
>
> **模型定位**：**线索筛选级**（拜访优先级排名），**不是成交概率预测**。

本文说明本次在智拓项目内落地的评分模型 v1：口径来源、交付内容、集成方式、
与参考实现的一致性验证结果、以及仍需业务确认的事项。

## 二、模型口径

### 2.1 总公式

```
Score = 100 × Σ ( βᵢ × xᵢ )     其中 Σβᵢ = 1，xᵢ ∈ [0,1]，Score ∈ [0,100]
```

### 2.2 八个特征（全部归一化到 0–1）

| # | 特征 | 公式 | 数据源 |
|---|---|---|---|
| 1 | 真实规模 | `clip(log1p(参保人数) / log1p(规模锚点))` | 参保人数（缺失记 0 分） |
| 2 | 资本实力 | `clip(log1p(注册资本万元) / log1p(资本锚点))` | 注册资本（缺失用中位数） |
| 3 | 方案线价值 | `clip((系数 − 2) / 3)` | 行业 → 16 条方案线（系数 2.0–5.0） |
| 4 | 方案契合 | `min(1,n1/3)×0.7 + min(1,n2/4)×0.3` | 企业名称/行业/经营范围/简介 命中关键词数 |
| 5 | 数字足迹 | `官网×0.45 + 企业域名邮箱×0.35 + 有简介×0.20` | 官网 / 邮箱 / 简介 |
| 6 | 触达可达 | `手机×0.40 + 邮箱×0.25 + 其他电话×0.15 + 地址分` | 联系方式 / 注册地址 |
| 7 | 拜访时效 | 按成立月数查表（见 2.4） | 成立日期 |
| 8 | 企业性质 | 外资/港澳台 1.0；法人独资 0.75；一般有限 0.5；自然人独资 0.4；合伙 0.3 | 企业(机构)类型 |

### 2.3 三个 beta 版本（特征相同，仅权重不同）

| 特征 | v1 均衡版 | v2 方案导向版 | v3 执行导向版 |
|---|---|---|---|
| 真实规模 | 18% | 12% | **26%** |
| 资本实力 | 10% | 6% | **16%** |
| 方案线价值 | 16% | **26%** | 12% |
| 方案契合 | 14% | **22%** | 8% |
| 数字足迹 | 10% | 14% | 6% |
| 触达可达 | 12% | 8% | **18%** |
| 拜访时效 | 12% | 8% | 10% |
| 企业性质 | 8% | 4% | 4% |

**推荐用法**：取 **v2 + v3 同时进入 A 级**的公司 = 「既有方案价值又有执行基础」的最优拜访池。
默认落库版本 = `v1-均衡版`（可在 config 的 `persist_version` 调整）。

### 2.4 分级与时效曲线

```
S — 优先拜访  Score ≥ 80      A — 重点拜访  70–79
B — 常规跟进  60–69           C — 培育观察  50–59        D — 暂缓  <50
```

| 成立月龄 | 系数 | 含义 |
|---|---|---|
| [0, 3) | 0.85 | 新设·专线刚需期 |
| [3, 6) | 0.90 | 启动期 |
| [6, 18) | 1.00 | 黄金期·云网ICT建设窗口 |
| [18, 30) | 0.80 | 扩展期 |
| [30, 42) | 0.57 | 稳定期 |
| [42, +∞) | 0.40 | 长期存续·续约扩容 |
| 缺失 | 0.50 | — |

### 2.5 锚点自适应（核心设计）

归一化分母是**数据分布的函数**，不是常量。写死 `500` 这类数值：换区域必然失效，
**在当前区域往往就已经是错的**（实测：硬编码 500 时，参保 100 人只能拿 0.742 分，
而它已是本批数据的 P99）。

| 项 | 当前值 | 说明 |
|---|---|---|
| 区域 | 深圳·福田区 | 改 `region` → 自动重标锚点 |
| 锚点模式 | `auto`（分位自适应） | 区域派单用 auto；省公司看板用 fixed |
| 参保人数锚点 | P95 = **40.95** 人 | 仅在非零值上取分位 |
| 注册资本锚点 | P95 = **500** 万元 | 全体取分位，下限 300 |

**锚点锁必须持久化**：保证同一区域多次评分结果一致。本项目落在数据库表
`scoring_anchor_locks`（按区域一条）；独立脚本落在 `scoring_anchors_lock.json`。

### 2.6 缺失值策略（两个特征故意不同，勿统一）

| 特征 | 策略 | 理由 |
|---|---|---|
| 真实规模（参保） | **记 0 分**（保守） | 参保是「有无真实雇工」的强证据；缺失大概率未实际经营 |
| 资本实力（注册资本） | **中位数填充**（中性，批级计算） | 资本缺失多属登记瑕疵，不代表企业无实力 |

## 三、三条铁律（本项目踩坑换来的）

1. **任何归一化分母都不能硬编码** → 一律走 `model_config.json` 分位自适应锚点。
2. **文本特征绝不能混入「标签侧描述文本」** → `方案契合` 的 blob 只含企业自身信息
   （名称/行业/经营范围/简介），**绝不含方案线自己的「典型方案」描述**。
   判断标准：*这段文本在拿到标签（方案线）之前就存在吗？*
3. **「文件重建了」≠「内容是最新的」** → 报告里所有数字从 `scoring_metrics.json` 动态派生，
   无手写统计值。

**防复发检查**（已内置）：
- `engine.self_check()`：行业映射覆盖率（未映射 < 15%，兜底桶 < 20%）；
- 特征诊断：`方案契合` 的标准差与封顶占比（若标准差偏低、封顶占比高 → 疑似泄漏）。

## 四、集成方式

### 4.1 API 端点

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/scoring/config` | 配置摘要 + 当前锚点 + 16 条方案线目录 |
| POST | `/api/v1/scoring/preview` | 对企业清单评分预览（不写客户库） |
| POST | `/api/v1/scoring/refresh` | 按工商档案重算已入库客户评分并落库 |

**示例（评分预览）**

```http
POST /api/v1/scoring/preview
{
  "region": "深圳·福田区",
  "rows": [
    {"企业名称": "深圳某某科技有限公司", "参保人数": "18", "注册资本": "791万元",
     "成立日期": "2024-04-10", "国标行业大类": "软件和信息技术服务业",
     "企查查行业中类": "机械设备", "企业(机构)类型": "有限责任公司（港澳台投资、非独资）",
     "官网网址": "example.com", "邮箱": "a@corp.com", "有效手机号": "13800000000",
     "注册地址": "深圳市福田区…", "经营范围": "智能机器人研发…", "企业简介": "…"}
  ]
}
```
行内既可用企查查原始列名，也可用规整键名（`name` / `insured_count` / `registered_capital` …）。

**示例（刷新已入库客户）**

```http
POST /api/v1/scoring/refresh
{"organizationId": "…（可选）"}
```
返回 `total / scored / changed / skipped / tierCounts / anchors`。
仅对 `extra_data.profile` 有工商档案的客户生效，其余计入 `skipped`。

### 4.2 导入即打分

`POST /api/v1/customers/import` 的请求行新增可选字段 `profile`。带 `profile` 的行导入时
按模型打分，结果写入：
- `Customer.score`（整数，落库版本分数）
- `extra_data.scoreDetail`（三版分数/分级、8 特征明细、方案线、锚点、基准日）
- `extra_data.reasons`（3 条可读理由）

评测失败时**降级**为沿用行内 `score`，不阻断导入。

### 4.3 独立运行（一键重建）

```bash
# 方式 A：直接跑（用内置样例）
python scripts/score_enterprise.py

# 方式 B：指定企业清单
python scripts/score_enterprise.py path/to/【企查查】高级搜索.xlsx --out output/enterprise_scoring

# 可选参数
#   --as-of 2026-10-06   计算成立月数的基准日（默认取当天）
#   --region 深圳·福田区  覆盖配置中的区域
#   --top 60             HTML 报告展示的 Top N
#   --no-lock            忽略锚点锁，强制重新标定
```

脚本**自动识别表头行**（扫描前若干行找含「企业名称」的行），因此无论表头在第 1 行
还是第 2 行都能读。产物：

```
output/enterprise_scoring/
├── 政企企业评分_三版本.csv     全量评分名单（含三版分数/分级/8 特征/联系方式）
├── scoring_anchors_lock.json   锚点锁
├── scoring_metrics.json        区分度/分级/方案线统计（报告的唯一数据源）
└── scoring_report.html         自包含 HTML 报告（中文·浅色商务风）
```

### 4.4 模型接管 `customers.score`（推荐商机链路）

「推荐商机」是**派生视图**，读的就是 `customers.score`。旧实现里有个陷阱：点「AI 更新商机」
会调用规则函数 `_score()` 把 `customers.score` 覆盖掉。现在已改为：

| 客户类型 | 谁算分 |
|---|---|
| **带工商档案**（`extra_data.profile`） | **企业评分模型**（批量、区域锚点锁一致） |
| 无工商档案 | 旧规则 `_score()` 兜底（模型依赖工商数据，无档案时不适用） |

- 触发入口：`POST /api/v1/opportunities/refresh`（前端「AI 更新商机」按钮）、
  `POST /api/v1/scoring/refresh`；两者都会调用模型。
- 客户导入时带 `profile` → **入库即由模型打分**。
- **单条 CRM 编辑不再孤立重算分数**：模型是批量的、依赖区域锚点，孤立重算会破坏锚点一致性；
  编辑后需重算请走上面两个 refresh 接口。

模型输出向前端暴露的字段（`GET /api/v1/opportunities`）：

```
modelDriven, modelVersion, tier, solutionLine, solutionCoefficient,
typicalSolution, features(8 项 0-1), scores(三版), tiers, anchors
```

### 4.4.1 评分基准日 `as_of`（决定「分数会不会变」）

模型用 **成立月数**参与「拜访时效」分档，所以**评分必须绑定一个基准日**。基准日解析优先级：

```
调用参数 asOf  →  model_config.json 的 as_of  →  date.today()
```

**`model_config.json` 里的 `as_of` 必须是一个固定日期，不能为 null。** 原因（踩过的坑）：

- 为 null 时回退到 `date.today()` → **分数每天漂移**（实测两天内 B 档 351→348、D 档 3287→3290），
  名单无法复现、无法审计；
- 且 `scoreDetail` 里含 `asOf`，而刷新时的"是否变化"判定会比对整个 payload
  → **跨天必然全员计入 `changed`（5000 家"变化"其实没变）**，这个数字完全没法用。

现在的做法：

| 项 | 行为 |
|---|---|
| 默认基准日 | `model_config.json` → `as_of`（当前为与 handoff 参考输出对齐的日期） |
| 显式覆盖 | `POST /api/v1/scoring/refresh` / `/preview` 传 `asOf` |
| 重复刷新 | **幂等**：同一基准日下 `changed = 0`、`metadataUpdated = 0` |
| 变化判定 | 只比对**影响分数的内容**，剔除 `asOf` 等易变元数据（`service._detail_content`） |
| 仅元数据变化 | 就地补正 `asOf`，计入 `metadataUpdated`，**不计入 changed、不 bump version、不写评分事件** |
| 重标定基准 | 改 `model_config.json` 的 `as_of`（或在调用时显式传 `asOf`） |

`GET /api/v1/scoring/config` 会回显 `asOf` 与实际生效值 `asOfIsPinned`，便于核对。

### 4.5 前端展示

| 位置 | 展示内容 |
|---|---|
| 推荐商机卡片 | 分数 + **等级角标**（S/A/B/C/D）→ 推荐原因 → **各部分得分构成轴** → 方案线（含价值系数） |
| 推荐商机筛选 | 关键词搜索 + 经营阶段 + 线索类型 + **评分等级（S/A/B/C/D，含各级家数）** |
| 客户详情弹窗 | **模型面板**：基准版本、综合分、等级、方案线、典型方案、三版分数、得分构成轴、锚点说明 |
| 客户导入（CSV） | 识别企查查列（参保人数/注册资本/成立日期/国标行业大类/企查查行业中类/企业(机构)类型/官网网址/更多电话/经营范围/企业简介）→ 组成 `profile` → 导入即打分 |

**得分构成轴**：把 8 个特征换算成「各自贡献了多少分」——

```
贡献分 = 该版权重 β × 特征归一值 × 100     （8 项之和 = 该企业的模型分）
例：培羽科技（v1-均衡版，总分 87.6）
    方案契合 14.00 · 真实规模 13.36 · 触达可达 12.00 · 方案线价值 10.67
    资本实力 10.00 · 数字足迹 10.00 · 拜访时效 9.60 · 企业性质 8.00
```

权重来自 `GET /api/v1/scoring/config`（前端取一次并缓存），**不在前端硬编码**，改配置立即生效。

**分值口径（展示 / 排序 / 阈值统一用「模型原始分」）**

模型输出的是 1 位小数（如 `59.6`），但落库的 `Customer.score` 是 `int(round(...))` 的整数。
**取整会把区分度砍掉一个数量级**，实测：

| 口径 | 同一分值最多并列 | D 档前 36 条的分值构成 |
|---|---|---|
| 整数分（旧，仅落库用） | **257 家** | 50 分 ×36 → **整屏一个分** |
| 模型原始分（1 位小数） | **56 家** | 49.9×20 · 49.8×12 · 49.7×4 |

因此前端**展示、排序、`≥80/≥75` 等阈值判断一律使用模型原始分**（`scoreDetail.scores[persistVersion]`，
前端由 `modelScoreFrom()` 取用），不再用整数分。好处有三：

1. 消除「筛选 C 时一屏全是 60 分、筛选 D 时一屏全是 50 分」的观感；
2. 顺带修掉「显示 60 分却是 C 级」的口径矛盾（等级本就按浮点算）；
3. 不碰数据库、不重算：小数分本来就在下发的 `scoreDetail.scores` 里。

同分时按 **方案线价值 → 企业名称** 次级排序；卡片在并列 >1 家时标注「并列 N 家」。
`Customer.score`（整数）**保持不变**，仍作为落库口径。

> ⚠️ 注意：任何回传后端的地方必须取整 —— `CustomerImportRow.score` / `CustomerUpdate.score`
> 都是 `int`，传小数会 422 整批/整表单失败（已在前端 `Math.round`）。

**搜索框输入法保护**：页面 `render()` 会整体替换 DOM，若在输入法组合（拼音等）过程中重绘，
`<input>` 会被换成新节点、候选词被中断（表现为打字卡顿/丢字）。现改为组合期间**只暂存取值、
不重绘**，`compositionend` 后再延迟重绘并恢复光标。

**列表展示条数**：推荐商机原先固定只渲染前 36 条，现改为可「显示更多」（每次 +60，
`ui.oppShown`）。

### 4.6 企业清单入库（Excel → PostgreSQL）

```bash
python scripts/import_customers.py "【企查查】高级搜索.xlsx"
python scripts/import_customers.py "企查查.xlsx" --limit 200 --dry-run      # 先试跑
```

读取 33 列 → 映射为导入行 + `profile` → 分批 `POST /customers/import`（≤1000 行/批）→
`POST /scoring/refresh` 复核并打印等级分布与 Top 10。

> 导入要求目标是 department 级组织；重复客户（同信用代码 / 同企业名 / 同手机号）自动跳过；
> 导入批次可通过 `POST /api/v1/customers/imports/{batchId}/rollback` 回滚。

## 五、一致性验证（对齐参考实现）

用 handoff 样例数据（100 家企业）× 参考锚点（参保 40.95 人 / 资本 500 万元）验证：

| 版本 | 与参考输出平均绝对差 | 最大绝对差 |
|---|---|---|
| v1-均衡版 | **0.00 分** | **0.0 分** |
| v2-方案导向版 | **0.00 分** | **0.0 分** |
| v3-执行导向版 | **0.00 分** | **0.0 分** |

**分级一致率 100%**，方案线映射一致率 100%。说明本模块与参考实现口径完全一致。

同时，`方案契合` 特征标准差 = **0.277**（参考实现修正后 0.279），封顶占比 38%，
与 handoff 记录的「剔除典型方案后标准差由 0.131 → 0.279」吻合 —— 印证 target leakage
防护生效。

### 5.1 真实清单入库口径核对（5000 家福田）

| 项 | 结果 |
|---|---|
| 清单行数 / 信用代码唯一数 | 5000 / **5000** |
| 同名企业 | **0** |
| 最终入库 | **5000** 家，全部带 `profile` + `scoreDetail` |
| 锚点 | 参保 40.95 人 / 注册资本 500 万元 |
| 等级分布 | S 14 · A 99 · B 351 · C 1249 · D 3287 |
| 榜首 | 培羽科技（深圳）有限公司 v1 = **87.6**（与 handoff 参考输出逐位一致） |

> **判重口径修正（重要）**：原实现按「同组织 + 同名」或「同组织 + 同电话」判重。
> 真实清单里信用代码全唯一、同名 0 条，却有 **235 家仅因与其他主体共用联系电话**
> 被判重丢弃（同一集团下的多家主体常共用一个联系人电话，例如「深圳熙恩医疗美容门诊部」
> 与其关联公司共用同一号码 —— 该企业模型评为 **A 级 75 分**，属于高价值客户）。
>
> 现规则：**只有导入行携带「真实业务身份」时才豁免手机号判重**。
> 真实业务身份 = 18 位**统一社会信用代码**（正则 `^[0-9A-Z]{18}$`，见
> `customers/service.py::_has_business_identity`）；交互式导入传的是前端本地占位 ID
> （形如 `c-m1abc2x3y`，见 `customerImportPayload`），**不算**企业身份，因此
> **新增线索 / CSV 导入 / 演示数据迁移 的手机号判重仍然生效**。
>
> ⚠️ 曾踩过的坑：最早写成「有没有传 `externalId` 就豁免」，而前端**总是**会传本地
> 占位 ID，于是把交互式导入的手机号判重整体关掉了（同一组织内同一电话可重复录入）。
> 回归用例见 `tests/test_customer_import_dedup.py::test_phone_dedup_applies_to_interactive_import`。
