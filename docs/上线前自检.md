# 上线前自检 · 并行开发约定

> 适用：`ZhiTuo-AI`（FastAPI + PostgreSQL + 单文件前端）
> 目的：把「会整站起不来」和「线上跑着旧代码」这两类问题挡在 push 之前。

---

## 一、push / 部署前跑这一条

```bash
cd ZhiTuo-AI
python scripts/preflight.py --api          # 迁移图 + 镜像一致性 + 接口冒烟
python scripts/preflight.py --tests        # 需要时再加跑后端测试套件
python scripts/preflight.py --all          # 全跑
```

退出码 0 = 全部通过；1 = 有失败，**先修再 push**。

| 检查 | 抓什么问题 | 需要什么 |
|---|---|---|
| `migrations` | 多 head / revision 撞号 / 悬空父节点 → 容器启动即失败 | 无（纯文件解析） |
| `image` | 改了代码但忘了重建镜像 → 线上跑旧逻辑 | Docker 已启动（否则自动跳过） |
| `api` | 登录、`/scoring/config`、`/opportunities` 是否可用 | 服务已启动 |
| `tests` | 后端回归 | 无 |

## 二、并行开发：迁移铁律

**背景**：本项目远端除 `main` 外还有多个同事分支（`feature/backend-foundation`、6 个 `codex/*`）。
两个人各自新增迁移时，最容易踩的是**双 head**。

**什么是 head**：迁移文件声明 `revision`（自己）与 `down_revision`（父节点）。
**没有被任何其他迁移当作 `down_revision` 的那个，就是 head**。head 代表"数据库结构的最新状态"。

**双 head 的后果**：`docker-compose.yml` 里 api 的启动命令是

```yaml
command: sh -c "alembic upgrade head && python -m app.scripts.seed && uvicorn ..."
```

`alembic upgrade head` 遇到多个 head 会直接抛
`CommandError: Multiple head revisions are present for given argument 'head'`，
`&&` 链**断在第一步** → seed 和 uvicorn 都不执行 → **api 容器起不来，整站不可用**。

更阴的是有人绕过它（`alembic upgrade <某个具体版本>`）：只执行了一个分支，
另一个分支的表永远不建 → 服务能起来，但一访问那个功能就 `UndefinedTable`。

### 铁律

1. **每次 push 前**：`git pull` → `alembic heads`（或 `python scripts/preflight.py`）→ 确认**只有一行**。
2. **生成迁移先 pull**：用 `alembic revision --autogenerate -m "..."`，
   它会自动把 `down_revision` 设成**你当前工作副本的 head**。分叉的根源永远是"拿过期副本生成迁移"。
3. **手写 `down_revision` 前先跑 `alembic heads`**，别凭记忆填一个"看起来是最后"的编号。
4. **出现双 head** → 生成一个空的合并迁移，把两个 head 收成一个：

```bash
alembic heads                                            # 看是哪两个
alembic merge -m "merge scoring into main line" <revA> <revB>
git add backend/migrations/versions/ && git commit
alembic heads                                            # 应只剩 1 个
```

> `alembic heads` / `alembic history` 只读迁移脚本，**不需要连数据库**；
> `alembic current`（看库里实际停在哪个版本）才需要连库。

## 三、回退：顺序错会让容器起不来

**必须先降级数据库，再回退代码。**

因为 api 容器每次启动都跑 `alembic upgrade head`。如果先回退代码（迁移文件被删），
而库里 `alembic_version` 还停在一个代码里已不存在的 revision，Alembic 会报
"Can't locate revision" → 容器反复重启。

```bash
docker compose up -d postgres
docker exec zhituo-ai-api-1 alembic downgrade <上一个版本>   # ① 先降库
git revert <sha>                                            # ② 再退代码
docker compose up -d --build
```

**其他必须知道的两点**：

- git 管不到业务数据。已入库的客户、评分、导入批次、审计事件**不会**随代码回退而消失，
  需要单独处理（建议按 `import_batch_id` 软删 `deleted_at`，可恢复）。
- `POST /api/v1/customers/imports/{id}/rollback` **只服务** `source_name == "现有HTML客户数据手动迁移"`
  的批次；企查查导入的批次会 **404**（来源名不符）/ **409**（已有评分变更事件），**不是通用回退**。

## 四、提交时别漏文件

新增的模块/迁移/脚本是**未跟踪文件**，`git add -u` 不会带上它们。

```bash
git add -A                 # 不要用 git add -u
git status --short         # 确认 改动(M) + 新增(A/??) 都在
python scripts/preflight.py
git commit -m "..."
git push origin main
```

漏掉迁移文件的后果：别人拉下来代码里有 `import`，库里却建不出表 → 一访问就报错。

当前约定：只改「给客户打分这一大块（前后端）」——
`backend/app/modules/scoring/`、迁移、`opportunities` 的序列化/刷新、`customers` 的导入与编辑打分、

以及旧演示模块 `matchProductResources` / `PRODUCT_RESOURCES` / `customerDemandProfile` /
后端 `opportunities._products`。要做范围外的改动请先对齐。

## 六、评分基准日（分数为什么会变）

模型用「成立月数」参与拜访时效分档，因此**评分绑定基准日**：

```
调用参数 asOf → model_config.json 的 as_of → date.today()
```

- `model_config.json` 的 `as_of` **不能为 null**（为 null 会回退到当天 → 分数每天漂移、名单无法复现）；
- 基准日不变时，`POST /scoring/refresh` 是**幂等**的（`changed = 0`）；
- 仅 `scoreDetail.asOf` 这类元数据需要补正时，只计 `metadataUpdated`，
  **不计入 changed、不 bump version、不写评分事件**；
- 核对当前基准日：`GET /api/v1/scoring/config` → `asOf` / `asOfIsPinned`。
