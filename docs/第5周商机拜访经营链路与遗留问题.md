# 第 5 周：商机与拜访经营链路

## 本轮完成

客户主档仍是商机的唯一事实来源，推荐商机继续作为未成交客户的派生视图；没有另建会与 CRM 失步的商机主表。

1. **评分日志**：客户导入写入带来源的评分基线；商机刷新、客户编辑、拜访结果改变评分或依据时写入服务端审计事件。未变化的重复刷新不生成空日志。迁移 `20260924_0007` 给已有客户补一条明确标记为“历史当前值”的基线，不伪称能恢复过去的评分过程。
2. **拜访计划**：新建任务保存创建当时的商机评分、推荐依据与阶段快照，同时记录计划事件。改期/改派和取消也记录操作者、前后值、原因；重复计划仍执行原有冲突检查。
3. **结果与成交**：完成任务时同步写入拜访结果、客户阶段、评分变化；有成交时记录产品与金额，并与拜访任务编号关联。重复完成请求仍以任务状态和版本阻止二次成交。
4. **统一追踪**：新增 `GET /api/v1/customers/{external_id}/journey`，按登录账号的数据范围返回评分日志、拜访计划、结果、成交及汇总。即使客户已成交、不再出现在推荐商机清单，仍可在 CRM 客户档案里查看全过程。前端沿用已有“查看流转”入口，没有给推荐商机增加第三个按钮。

## 关键数据口径

- `scoreLog`：保留前后评分、评分依据、触发原因、数据来源和规则版本。`migration_baseline` 表示旧数据迁移时的当前值；`import_baseline` 表示本轮之后入库时的初始值，后两者的原始计算过程未被验证。
- `visits[].opportunityScoreAtPlan`、`opportunityScoreEventIdAtPlan`：建计划时的评分快照与对应评分事件编号，不随之后的重新评分改变。历史迁移任务没有这个快照，接口返回 `null` 且标记 `legacy_import_unavailable`。
- `deals[]`：从已完成且金额大于 0 的拜访任务读取；金额使用字符串保留两位小数。此处是**客户经理回填的经营记录**，不是已与合同或计费系统核对的财务收入。
- 组织和角色权限由后端校验。客户经理只能看到其可见客户下本人负责的任务；上级按原有组织范围查看下级数据。

## 验证结果

- 既有第 4 周基线：34 项测试通过，前端脚本语法检查通过。
- 本轮增加历史评分迁移、评分到成交全链路、重复刷新/成交、跨组织拒绝、跨区转派评分依据、旧任务无评分快照等测试；完整回归 37 项通过。
- Alembic 从空 SQLite 库升级到 `20260924_0007` 成功，并用含旧客户数据的库验证评分基线回填。代码静态检查与前端脚本语法检查通过。
- 当前机器仍未找到 Docker CLI，因此**尚未在 PostgreSQL 容器上完成实际部署验收**。在有 Docker 的环境需运行 `docker compose up --build -d`，检查 `/api/v1/health/ready`，再用真实登录账号走一次客户编辑、评分刷新、创建拜访、结果回填和链路查看。

## 之前问题的复查与后续待办

1. **旧浏览器历史与本地审批**：第 4 周记录的问题仍在。旧 `stageHistory` / `crmFlow` 无法倒推真伪；旧浏览器本地审批不是共享审批。需要和团队决定迁移、标记或归档策略，本轮不擅自删除。
2. **人员主数据**：部分客户经理只有姓名、没有后端账号，`owner_user_id` 可能为空。需要补齐人员与组织关系，明确调岗/离职后的客户和任务归属规则。
3. **部署与安全**：当前端口仍绑定本机 `127.0.0.1`；跨电脑共享要部署可访问的服务，并配置 HTTPS、密钥、备份、审计留存与权限回归。应用级事件表不等同监管级不可篡改审计。
4. **历史拜访任务快照**：迁移前任务无法恢复计划当时的真实评分，只能显示“无快照”；不应拿当前评分伪装成当时评分。
5. **成交确认口径**：目前金额由用户回填，缺少合同/订单/计费系统凭证；同一客户多笔成交是否允许、如何冲销或更正需要业务方定义后再建正式成交审批和对账链路。
6. **评分规则**：现在是可解释的静态规则，不是经过真实转化数据校准的预测模型。正式使用前需要数据质量检查、权重评估与版本管理。
