# 第 4 周：CRM 写链路交付与待办

## 本轮交付

- 客户资料编辑仍使用 `PATCH /api/v1/customers/{external_id}`，带 `version` 做并发检查。字段变更、经营阶段变化由服务端记录操作者、时间、前后值和原因；浏览器提交的 `stageHistory`、`reasons`、`score` 不再作为权威值，评分与推荐原因由后端重新计算。
- 如果同时改动客户归属地或客户经理，前端在同一次 PATCH 中提交 `ownershipRequest`。基础资料保存、阶段记录、归属审批申请同属一个数据库事务；任何一步失败均不落库。归属与经理在直属上级审批前维持原值。
- 归属变更和删除使用同一张 `customer_requests` 表、同一审批列表与决策接口。申请人不能自批；驳回必须说明原因；批准归属变更后同步更新未完成拜访任务负责人；批准删除仅软删除，业务列表不再显示，审批记录与审计数据保留。
- 新增 `customer_events` 追加式审计表，记录客户资料编辑、阶段变更、归属/删除申请及审批结果。客户详情接口返回最近 200 条 `auditEvents`，页面详情展示最近 12 条。数据库迁移为 `20260924_0006`。
- 拜访任务完成引起的客户阶段变化，同样写入该审计表，保留第 3 周拜访与推荐商机链路。

## 关键接口约定

```json
PATCH /api/v1/customers/c-001
{
  "version": 2,
  "name": "某企业有限公司",
  "industry": "信息技术",
  "contact": "张经理",
  "phone": "13800000000",
  "need": "企业专线",
  "stage": "已联系",
  "stageReason": "电话确认了初步需求",
  "potential": "高",
  "score": 80,
  "nextAction": "安排拜访",
  "isQianBaiWanGroup": "否",
  "isKeyAccount": "否",
  "ownershipRequest": {
    "targetOrganizationId": "组织 UUID",
    "targetOwnerName": "目标客户经理",
    "reason": "客户归属调整的具体原因"
  }
}
```

`ownershipRequest` 可省略；若填写，必须有目标组织、经理和不少于 5 字原因。`score` 字段暂时保留以兼容旧调用方，但服务端忽略传入数值。阶段变化时 `stageReason` 必填。旧的独立 `POST /customers/{id}/requests` 接口仍可提交归属变更或删除申请。

## 后续待解决（本轮不隐瞒、不假定已完成）

1. 旧 HTML 导入数据里的 `stageHistory` / `crmFlow` 来自浏览器，无法追溯确认真实性。本轮之后的新操作均由服务端生成审计事件；旧历史需要另行标记为“迁移记录”并制定核验策略。
2. 部分历史客户经理只有姓名、没有对应后端用户。归属审批目前可保留这个姓名，`owner_user_id` 为空；因此按账号归属的严格权限和通知能力会受影响。需要补齐人员主数据并确认离职、调区的处理规则。
3. 浏览器本地仍保留旧版审批记录，它们只在原浏览器可见，不能当成团队共享审批。需确定迁移或归档策略，再移除本地兼容分支。
4. 完整生产审计还需要不可篡改存储、备份恢复、敏感字段脱敏/访问日志与保留期限。本轮的数据库事件是应用层追加式记录，不等于监管级不可篡改审计。
5. 当前 Docker 配置将服务映射到 `127.0.0.1:8000`，只允许宿主机访问；团队跨电脑共享仍需部署可访问的服务器、HTTPS 与生产安全配置。
